# 神兽竞技场当前项目目录结构审查报告

版本：v1.1  
初次审查日期：2026-07-12  
实现状态更新：2026-07-15  
审查范围：仓库根目录、UE 游戏工程、后端、管理后台、官网、启动器、文档与证据目录。  
审查方式：只读检查当前文件系统、Git 状态、忽略规则、工程描述文件及既有三层架构文档；未移动、删除、重命名、保存资产，也未运行自动化测试或 PIE。

## 1. 结论摘要

当前仓库已具备合理的单仓库产品边界：`DBA_GameClient`、`DBA_GameBackend`、`DBA_GameAdmin`、`DBA_GameWebsite`、`DBA_GameLauncher` 职责明确。UE C++ 模块仍维持 `DivineBeastsArena -> GameMoba -> GameCore` 的物理依赖方向；根目录 `AGENTS.md` 是唯一权威协作规则，其余 Agent 入口已收敛为兼容说明。

主要结构风险不在应用工程是否拆分，而在以下三处：

1. UE `Content` 仍同时存在新正式域 `/Game/DBA` 与多个旧顶层资源域，资产归属、迁移状态和引用审查需要继续受控收束。
2. 当前工作区有 **910 项** Git 变更，集中于 `DBA_GameClient`、`scripts`、`Artifacts` 与后端，任何大规模目录操作都会放大回滚和审查风险。
3. `docs/` 与 `DBA_GameClient/Docs/`、根目录 `Artifacts/` 与后端 `artifacts/`、根目录 `backups/` 的归属规则尚未完全显式化，容易继续积累重复文档和非源文件。

本报告建议采用“先定义唯一归属与迁移登记，再由 Editor/MCP 按引用迁移”的路线；不建议在当前脏工作区内进行批量文件系统移动。

## 3. UE 工程结构审查

### 3.1 C++ 模块

`DBA_GameClient/Source/` 当前包含：

| 模块 | 定位 | 审查判断 |
| --- | --- | --- |
| `GameCore` | 通用会话、异步、基础 UI、数据与跨端能力。 | 基础层存在项目身份与冻结构筑语义泄漏风险，需按既有报告逐步清理。 |
| `GameMoba` | 可复用 MOBA 抽象、GAS/HUD 基类与桥接能力。 | 目录规范正确，但通用层仍偏薄，不能机械上移项目逻辑。 |
| `DivineBeastsArena` | 十二生肖、元素、五营、项目 GAS、角色、前台、HUD、VFX 与项目流程。 | 作为项目业务层合理，是业务身份和规则的唯一归属目标。 |
| `Plugins/GameBackendClient` | UE 到后端的插件边界。 | 合理；对外访问必须继续遵循异步与中文错误日志策略。 |

`Public/Private` 物理划分保持 UE 标准。后续不应新增第四套项目业务模块或新的通用类型前缀；跨层业务身份应优先由 Arena 数据资产、稳定 ID 与适配器控制。

### 3.2 Content 资产域

当前 `Content` 一级目录共 20 个，资产量较高的目录包括：`DBA`（615）、`ProjectileHitVFX`（365）、`Animation`（144）、`Blueprints`（89）、`UI`（87）、`Audio`（48）、`VFX`（48）、`Maps`（28）。

| 分类 | 当前目录 | 判断与规则 |
| --- | --- | --- |
| 正式项目域 | `DBA/` | 应作为项目正式资源的唯一主域。十二生肖正式资源已开始收束至 `/Game/DBA/Zodiacs/Chinese`。 |
| 历史/迁移来源 | `Animation/`、`Models/`、旧 `Blueprints/`、旧 `UI/`、旧 `VFX/` 等 | 不得直接删除。需先记录引用、迁移目标和退役条件，再通过 Unreal Editor/MCP 事务迁移。 |
| 第三方或样例 | `Characters/`、`FrostMage/`、`Templates/`、`ProjectileHitVFX/` | 应标明来源、许可证、是否允许运行时引用；不应与项目正式资源混杂。 |
| 项目地图 | `Maps/` | 合理保留在顶层；地图命名、流送资源与项目 UI 关联应在地图登记表中可追溯。 |
| 临时生成 | `_AutoPlaceholders/`、`MCP_Generated/`、`Developers/` | 不得成为正式运行时依赖。`MCP_Generated` 中已审核资产应迁入正式域，未审核项需显式标为实验资产。 |
| 制作输入输出 | `SourceArt/`、`SourceAssets/`、`Exports/` | 不应放入 `Content`；当前位于工程根目录是合理方向，但需补充 README、来源、导入目标与交付责任人。 |

十二生肖资源已确定的规则必须继续执行：玩家选角、创建角色与大厅角色只读取 `DA_DBA_ZodiacCharacterRegistry` 和 `DA_DBA_ZodiacCharacterSelection`；禁止按照 C++ 路径或旧目录回退。`/Game/Models/Zodiac` 与 `/Game/Animation/Zodiac` 当前仅作为迁移来源，待引用审查完成后再退役。

## 4. 非 UE 工程与文档审查

### 4.1 后端

后端现已按 `Game.Api`、`Game.Application`、`Game.Worker`、`Game.ServerManagement`、`Game.Infrastructure`、`Game.Shared` 与测试项目拆分，服务端进程、应用用例和基础设施已具备物理边界。

截至 2026-07-15，角色列表/创建/选择、角色构筑、一次性入服票据、连接信息签发、房间/匹配建会话、服务器地址分配、会话查询与生命周期状态机均已形成 `Game.Application` 用例或端口；EF Core 仓储与密码学实现位于 `Game.Infrastructure`。`SessionService` 已移除 `GameDbContext`、EF Core、数据库实体、角色默认值、令牌实现和会话状态机，只保留用例调用与共享 DTO 映射，文件规模已由约 450 行收缩至约 145 行。认证域已按相同方式完成当前账号身份查询、访客登录、正式账号注册、普通/开发账号凭据认证、JWT 登录凭据签发、刷新令牌持久化、刷新令牌原子轮换、登出撤销、密码修改和密码重置拆分；刷新令牌会保存真实 IP 与 User-Agent，同一旧刷新令牌在 PostgreSQL 中通过事务和条件更新保证只能消费一次。密码规则、账号初始数据、访客名称规则及全部认证响应文案均由 `AuthenticationPolicy` 配置驱动，密码更新与全部登录会话撤销在同一事务中执行。`AuthService` 已由约 466 行收缩至约 231 行，并完全移除 `GameDbContext`、EF Core、数据库实体、密码算法和设备哈希依赖。

认证并发约束已同步增强：`player_identity.display_name` 和 `device_login.device_id_hash` 均使用全局唯一索引，避免并发注册同名账号或同一设备首次登录时创建重复账号；`device_login.account_id` 保留普通查询索引。`20260715104002_EnforceAuthenticationIdentityUniqueness` 已在本地开发库应用，迁移前后显示名与设备哈希重复组均为 `0`。迁移包含中文重复数据保护，其他环境发现历史重复时会停止，不会自动删除或合并账号。

后续应维持现有项目边界，将同样的模式扩展到仍直接依赖 EF Core 的其他大型 API Service；API 只负责协议映射，Application 负责用例和状态规则，Infrastructure 负责 EF Core 与外部系统。会话来源已新增 `(source_type, source_id)` 条件唯一索引 Migration，并在并发唯一约束冲突时回读既有会话；2026-07-15 已在本地开发库应用 `BindJoinTicketAdmissionContext` 与 `AddSessionSourceUniqueness`，索引定义核验通过，迁移前后重复来源均为 `0`，过程中未删除或合并历史数据。连接凭证提交已使用旧 `session_token_hash` 与 `left_at` 作为乐观并发条件，避免并发签发导致多个请求同时成功。EF 设计时工厂已移除数据库账号与密码硬编码，开发 Compose 与开发配置中的凭据改由环境变量注入。`deploy/secrets/` 本次仅检查目录与文件名，未读取任何敏感内容；该目录需要确认只包含模板或未被版本控制的本地文件。

## 5. Git 与生成物治理

本次检查时工作区有 **910 项** 变更：`DBA_GameClient` 421 项、根 `scripts` 211 项、`Artifacts` 178 项、`DBA_GameBackend` 44 项，其余为文档、前端与根治理文件变更。该状态不表示这些改动有误，但意味着当前不适合做批量迁移、目录重命名或清理。

`.gitignore` 已覆盖 UE 的 `Binaries`、`DerivedDataCache`、`Intermediate`、`Saved`，以及 Web 的 `node_modules`、`.next`、`.angular`、`dist` 和 Rust `target`。这些目录虽在本地存在，但不是受控源码，不应纳入本次重构范围。

`README.md` 当前声明项目禁止自动化脚本、CI 工作流、自动登录、自动选角、自动匹配和自动旅行。仓库仍可见 `scripts/`、`DBA_GameBackend/scripts/`、`tools/`、`load-tests/` 等目录时，应逐个区分“人工启动辅助/历史工具/待删除入口”，不能据目录名直接删除；任何清理必须先进行引用和交付依赖审查。

## 6. 推荐修改计划

### 阶段 A：建立目录所有权与迁移台账

1. 在 `docs/Architecture/命名与目录登记表.md` 中登记顶层目录所有者、允许内容、是否可直接提交和保留策略。
2. 为 `Content` 的每个一级域标明“正式、迁移来源、第三方、实验、地图或制作输入输出”。
3. 对 `backups/`、根 `Artifacts/`、后端 `artifacts/` 建立索引，不做删除。

验收：新增资源、文档和证据均能找到唯一归属；任何迁移项都有来源、目标、引用状态和回滚说明。

### 阶段 B：受控收束 UE 资产

1. 优先完成十二生肖旧资源引用审查，继续保持 Registry/Selection 数据资产为唯一读取入口。
2. 按角色、UI、VFX、音频、数据、地图逐批建立迁移清单，禁止跨域批量剪切。
3. 通过 Unreal Editor/MCP 完成每一批资产迁移，保留 Undo Transaction，执行 Compile、Save、引用检查和人工界面验证。
4. 只有引用为零且人工审核完成后，才在单独任务中退役旧目录资源。

验收：运行时不再直接依赖迁移来源路径；DataAsset 能完整表达所有正式资源引用；每批均可回滚。

### 阶段 C：收敛代码与文档边界

1. 按既有三层报告，将项目身份模型和固定构筑规则从 `GameCore` 迁回 Arena 数据与业务层。
2. 会话域和认证域首轮 Application/Infrastructure 拆分、来源/身份唯一约束、凭证并发保护及本地开发库迁移已经完成；下一步准备 API、Dedicated Server 与两个可见客户端进行登录到大厅人工联调，并按相同模式迁移其他仍直接依赖 EF Core 的大型 API Service。禁止重新把跨系统编排堆入 Endpoint、`SessionService` 或 `AuthService`。
3. 建立 `docs/` 与 `DBA_GameClient/Docs/` 的索引页，只迁移确定重复且无外部链接依赖的文档。

验收：项目业务身份只有一个权威定义；文档索引可定位权威版本；新增代码符合 C++ 逻辑、DataAsset 配置、事件 UI 与异步接口策略。

### 阶段 D：恢复可审查的工作区基线

1. 按功能域拆分当前 910 项变更的人工审查批次，不使用重置或批量清理。
2. 对每批确认来源：源码、资产、文档、人工验证证据或历史删除。
3. 仅在人工审核确认后提交或归档；生成物继续由忽略规则排除。

验收：每项未提交变更都有归属和处理决定，后续目录迁移可在小而可回滚的变更集中进行。

## 7. 本轮限制与后续动作

本轮没有修改工程结构、没有删除冗余文件、没有移动任何 UE 资产、没有读取密钥文件，也没有执行自动化测试、PIE 或构建。唯一写入是本审查文档。

下一步应先准备 API、Dedicated Server 与两个可见客户端窗口，由人工审核登录、选择或创建角色、获取大厅分配、JoinTicket 校验及大厅角色同步；人工结论记录完成后，再执行阶段 A 的目录与资产域登记，并以十二生肖正式资源迁移作为第一批受控收束对象。这样既符合人工运行审核策略与 DataAsset 唯一入口策略，也避免在脏工作区内制造新的路径回退或引用断裂。
