# DivineBeastsArena 三层架构、工程目录与命名审查报告

版本：v1.1  
日期：2026-07-12  
审查范围：UE 客户端与 Dedicated Server、后端、管理后台、官网、启动器、根目录治理文件、CI 与受版本控制的工程目录。  
审查原则：以当前仓库实际代码和目录为事实依据；目标架构仅作为整改方向，不把文档中的理想结构误写为已完成状态。

## 0. 2026-07-12 整改状态

本次复核确认 UE 模块物理依赖仍保持 `DivineBeastsArena -> GameMoba -> GameCore` 与 `DivineBeastsArena -> GameCore`，未发现反向模块依赖或跨模块 Private include。

已完成的低风险整改：删除 CI 工作流；移除空的自动化工具目录；删除拼写错误的 `ANGENT.md`；将 `AGENT.md`、`CLAUDE.md`、`CODEX.md` 收敛为指向 `AGENTS.md` 的兼容入口；统一 Website 与 Launcher 的发布包命名；更新目录规范以禁止自动化脚本和自动化验收入口。

未直接搬迁 `GameCore` 中的身份枚举和冻结构筑规则。该项仍是 P0：现有代码与 UE 资产、网络旅行、存档和数据表约有 102 个源码引用，必须在人工审核的分阶段迁移中完成，不能用文件系统批量移动或机械重命名替代。

## 1. 执行摘要

项目已经具备可运行的单仓库形态，以及可被脚本检查的 UE 三层模块依赖：

~~~
DivineBeastsArena -> GameMoba -> GameCore
DivineBeastsArena -> GameCore
~~~

本轮执行 scripts/validate-unreal-module-boundaries.ps1，结果为通过。三个模块的 Build.cs 方向、跨模块 Private include 和父目录 include 均没有发现违反当前规则的情况。

但“依赖方向正确”不等于“三层职责正确”。当前最大架构风险是 Foundation 语义泄漏与项目身份模型双份定义：

1. GameCore 内含 EDBAZodiac、EDBAElement、EDBAFiveCamp、FDBACharacterBuildSummary 和 Zodiac + Element -> FixedSkillGroupId 推导规则。
2. DivineBeastsArena 又定义了 EDBAZodiacType、EDBAElementType、EDBAFiveCampType。
3. 角色、技能、HUD、VFX 与数据表之间存在多处显式转换辅助函数。

这使 Foundation 实际知道十二生肖、元素和五营业务，同时 Arena 层还要维护平行类型。短期可编译，长期会导致序列化、DataTable 行名、网络旅行参数、UI 与 GAS 参数在不同类型间持续增加转换补丁。该问题应作为 P0 优先整改。

## 3. 当前架构事实

### 3.1 UE 三层模块

| 模块 | 源码文件数量 | 当前职责事实 | 判断 |
| --- | ---: | --- | --- |
| GameCore | 65 | 登录、账号、前台会话、队列、对象池、通用 UI、DataAsset 基类、异步数据表加载、构筑传输对象。 | 基础能力较完整，但混入项目身份和构筑规则。 |
| GameMoba | 19 | GameMode、ASC/Ability 基类、RPC、HUD Controller、UI 基类及 GameCore 类型桥接头。 | 依赖方向正确，但仍是偏薄的通用骨架。 |
| DivineBeastsArena | 381 | 生肖、元素、五营、GAS 扩展、战斗、角色、前台、HUD、VFX、数据与项目流程。 | 主要业务集中地，目录总体符合 UE 的 Public/Private 约定。 |

优点：

- Public 下未发现 .cpp；2026-05 审计发现的 Public 实现文件问题已经得到修复。
- DivineBeastsArena.Build.cs 对 RenderCore、RHI、AudioMixer、MediaAssets 使用了 Target.Type != TargetType.Server 保护。
- GameMoba 依赖 GameCore，未反向依赖 DivineBeastsArena。
- GameCore、GameMoba、DivineBeastsArena 都保持一层模块根目录加 Public/Private 的 UE 标准布局。

## 4. 目录与命名评估

### 4.1 合理部分

- UE C++ 模块目录、类名前缀 DBA、U/A/F/E/I 类型前缀与 Public/Private 分离基本一致。
- 后端项目按 Host、Infrastructure、Shared、Worker、ServerManagement 进行了物理拆分，比单体 Web API 更易演进。
- Admin 的 core/layout/pages，Website 的 app/components/data/lib，Launcher 的 src/src-tauri 都符合各自框架习惯。
- Binaries、Intermediate、DerivedDataCache、Saved、node_modules、.next、dist 均未被版本控制，Git 卫生基础良好。

### 4.2 需要统一的命名

| 范围 | 当前问题 | 推荐规则 |
| --- | --- | --- |
| UE 工程目录 | DBA_GameClient 同时承载 DS。 | 近期保留物理目录，文档统一称“UE 游戏工程”；中长期评估迁移为 DBA_GameUE，不做一次性重命名。 |
| UE 模块 | 模块名与内部根目录 GameDBA、类型前缀 DBA 并存。 | 保持模块名不动；规定 Arena 公共类型放 GameDBA，类前缀统一 DBA，禁止新增 ArenaGame、ZodiacArena 等第三套前缀。 |
| 跨层类型 | GameCore 与 Arena 同时有身份枚举。 | 一个业务身份只允许一个权威 UENUM；跨层传输使用稳定 ID、GameplayTag 或 DTO。 |
| GameMoba 桥接头 | 与 GameCore 同名，无法一眼识别所有权。 | 过渡期标为 DeprecatedBridge 或直接让调用方 include GameCore；长期仅保留真正的 Moba 类型。 |
| 后端项目 | Game.Shared 同时承载 Contracts、Common、Errors、Options。 | 近期保持名称；新增 Game.Application 后，将用例、端口和命令查询从 Api/Shared 归位。 |
| Web 包名 | Website/Launcher 缺少 DBA 前缀。 | npm/crate 显式统一为 dba-game-website、dba-game-launcher；变更同时更新发布与 CI 元数据。 |
| 治理文件 | 多个 Agent 指令文件且内容不同。 | AGENTS.md 为唯一权威；其他文件先改为短说明和指向链接，稳定后在单独变更中删除。 |

## 5. 最佳目标架构

### 5.1 UE 逻辑边界

~~~
GameCore
  通用异步、日志、账号会话、平台、网络协议 DTO、资源加载、基础 UI
  不认识 Zodiac / Element / FiveCamp 业务枚举

GameMoba
  可复用 MOBA 战斗抽象、ASC/Ability/Attribute 基类、队伍与目标选择、
  通用 HUD Controller、输入槽与战斗状态
  不认识具体生肖、五营、项目 UI、项目数值表

DivineBeastsArena
  Zodiac / Element / FiveCamp 的唯一业务模型、固定技能组、项目 DataTable、
  角色、项目 GAS、项目 UI/VFX、地图与赛前选择
~~~

跨层传输不再直接泄漏 Arena UENUM：

~~~
Arena 业务类型
  -> Arena Adapter
  -> GameCore 中性传输 DTO（稳定 FName / GameplayTag / 字符串协议字段）
  -> 后端/旅行参数
  -> Arena Adapter
  -> Arena 业务类型与 DataTable 校验
~~~

这不是把规则下沉到 DTO。DTO 只携带身份 ID 和版本；FixedSkillGroupId 的合法性、生肖元素映射、五营表现和数值校验仍只由 Arena 数据资产和 Dedicated Server 执行。

### 5.2 后端逻辑边界

~~~
Game.Api / Game.Worker / Game.ServerManagement
  进程宿主与组合根：HTTP、后台任务、运维入口、DI 装配
      -> Game.Application
        用例、命令、查询、权限编排、端口接口、事务边界
          -> Game.Shared 或未来 Game.Domain
            协议契约、值对象、错误码、领域规则
      -> Game.Infrastructure
        EF Core、Redis、文件、外部平台与端口实现
~~~

宿主项目在组合根引用 Infrastructure 是可接受的；不应让 Endpoint、Hub 或 Controller 直接承载跨聚合业务编排，更不应让 Shared 继续累积 Infrastructure 细节。

### 5.3 资产与工具边界

~~~
Content/DBA
  Core            共享样式、基础 DataAsset、通用表现
  Moba            仅可复用 MOBA 资源
  Arena           Zodiac、Element、FiveCamp、地图、项目 UI、项目 VFX/SFX
  Data            运行时 DataTable、PrimaryDataAsset、配置表
  Experimental    经过审批的 MCP_Generated 演示资产

DBA_GameClient/SourceArt
DBA_GameClient/SourceAssets
DBA_GameClient/Exports
  保留为 UE 制作链输入/输出，但补充 README、来源、生成命令和交付归属。
~~~

资产迁移只允许通过 Unreal Editor/MCP 事务完成，必须 Compile、Save、引用检查、PIE Smoke Test；禁止文件系统移动 .uasset 或 .umap。

## 6. 最佳修改计划

### 阶段 0：先建立不可回退的基线

目标：先让“语义越层”也能被自动发现，再移动任何类型。

1. 新增架构决策记录，定义 Foundation、Moba、Arena 允许的概念词、Public API 与依赖例外。
2. 扩展 validate-unreal-module-boundaries.ps1：
   - GameCore 禁止新增 Zodiac、Element、FiveCamp 业务 UENUM/USTRUCT。
   - GameCore 禁止新增固定技能组推导和具体 DataTable 行名规则。
   - GameMoba 禁止新增 Zodiac、FiveCamp、项目资源路径与项目 Widget 名称。
   - 允许白名单仅用于迁移适配器，并要求带到期日期和测试。
3. 为模块边界脚本、源码守卫和 Dedicated Server Target 建立 CI 作业。
4. 建立 docs/Architecture/命名与目录登记表.md，记录模块、公共类型、DataAsset、PrimaryAssetType、目录所有者和弃用期。

验收：

- 新增反向依赖、跨层业务枚举、跨模块 Private include 在 CI 中失败。
- 现有白名单具有责任人、迁移目标和删除条件。

### 阶段 1：消除身份模型双源

目标：让 Zodiac、Element、FiveCamp 只有一个 Arena 权威模型。

1. 在 Arena 层确定唯一 UENUM 命名，以当前资产、网络和 UPROPERTY 使用最广的类型为基线；不要仅为命名好看而重新编号。
2. 在 GameCore 新建中性 BuildTransport DTO，只含稳定 ID、版本、玩家/会话标识和不透明构筑引用，不含业务枚举与技能规则。
3. 在 Arena 新建单一 BuildIdentityAdapter：
   - 将 Arena UENUM 与中性 DTO 互转。
   - 通过 DataTable/PrimaryDataAsset 校验稳定 ID。
   - 输出中文、可定位的缺失配置日志。
4. 按“登录与创建角色 -> 旅行参数 -> Dedicated Server 准入 -> HUD 展示”顺序迁移调用点。
5. 删除 GameCore/Character/DBACharacterBuildTypes 中的业务枚举依赖、MakeFixedSkillGroupId 与 FiveCamp 决策；对应规则回归 Arena 数据层。
6. 最后删除 Arena 内分散的 ToCommonZodiac、ToCommonElement 等局部转换函数。

验收：

- GameCore 源码不再定义或消费 Zodiac、Element、FiveCamp UENUM。
- Arena 只保留一套权威身份 UENUM。
- 60 条固定技能组数据表、旅行 URL、后端冻结构筑摘要、Dedicated Server 准入和登录到大厅回归全部通过。
- 旧 UPROPERTY/序列化字段使用 Core Redirect 或显式版本迁移，不能静默丢档。

回滚：

- 每次仅迁移一条链路；保留受测试保护的 Adapter 双读期。
- 只有所有资产重保存、序列化测试和联机验证通过后才删除旧字段。

### 阶段 2：让 GameMoba 成为“少而真”的通用层

目标：不把 Arena 代码机械上移，只提炼至少两个项目都会复用的概念。

1. 为每个候选类建立归属检查：是否不依赖 Zodiac/Element/FiveCamp、是否至少存在两个 Arena 功能域复用、是否可在 Dedicated Server 单独运行。
2. 优先提炼通用 ASC/Ability/Attribute 基类、Targeting、Damage 输入输出、Team/Targetable 接口、通用技能槽与 HUD WidgetController 协议。
3. 保持元素克制、生肖大招、五营表现、项目 DataTable、角色创建 UI、项目 VFX 在 Arena。
4. 将 GameMoba 的同名桥接头标记为迁移 shim，逐步改为直接引用真正的 GameCore 头；等无调用后删除。
5. 补充 GameMoba 独立 Automation Tests，至少覆盖 GAS 基类、目标选择、队伍关系与 HUD 事件协议。

验收：

- GameMoba 新增代码不引用 GameDBA。
- GameMoba 测试可以不加载项目生肖资产而运行。
- 从 Arena 下沉的每个类型都有复用证明和行为回归。

### 阶段 3：后端引入应用层

目标：控制 API、Worker、Dedicated Server 管理和 Infrastructure 的耦合。

1. 新建 Game.Application，先迁移登录、角色、会话/旅行、结算四条跨端关键用例。
2. 把端点保留为输入验证、身份提取和 HTTP 映射；把业务编排迁入 Application Handler/Service。
3. 用接口表达数据库、缓存、Dedicated Server Runtime、邮件和外部平台端口；Infrastructure 实现这些接口。
4. Api、Worker、ServerManagement 仅在组合根注册 Infrastructure，不在 Endpoint 中直接访问 EF/Redis 实现。
5. 逐步将 Game.Shared 收敛为 Contracts、错误码和值对象；避免把应用服务继续堆入 Shared。

验收：

- 新增跨聚合业务不在 Endpoint、Controller、Hub 中实现。
- Application 单元测试不需要启动 Web Host 或真实数据库。
- 登录、选角/创建、进入大厅、Dedicated Server 会话和结算集成测试继续通过。

### 阶段 4：目录、资产和命名收敛

目标：解决双轨目录，不做高风险“大搬家”。

1. 为 Content 顶层每个目录建立归属清单：保留、迁入 Content/DBA、外部样例、待删除或仅开发资产。
2. 优先处理新资产：所有新增 DBA 业务资产只允许进入 Content/DBA 规范子目录。
3. MCP_Generated 改为显式实验区，增加 Cook 白名单/黑名单与引用扫描；确认需要量产的资产后才通过 Editor 迁入正式目录。
4. 旧资产按“一个目录、一类资产、一轮引用验证”迁移，不混入源码重构。
5. 为 SourceArt、SourceAssets、Exports、Tools、Scripts 新增目录 README，说明输入、输出、权威来源、生成命令和 Git 策略。
6. 统一 npm/crate 发布名，并更新 CI、启动器更新清单、遥测维度和文档。

验收：

- 新资产无新增双轨目录。
- 每次资产移动均有 Editor 引用检查、Cook、PIE 和 Git Diff 证据。
- 包名、构建产物名与发布清单使用同一 DBA 命名表。

### 阶段 5：治理与持续验证

目标：一个规则来源、一条可追溯证据链。

1. 保留 AGENTS.md 为唯一权威协作规则；其他根治理文件先改成短链接页，确认无工具依赖后删除。
2. Artifacts 建立 manifest、保留期和“长期证据/瞬态日志”分类；backups 改用仓库外受控备份或明确保留清单。
3. CI 增加：
   - UE 模块边界与源码守卫。
   - Win64 Editor 编译。
   - Dedicated Server 编译或打包烟测。
   - 关键 Automation Tests。
   - 后端、Admin、Website、Launcher 既有构建测试。
4. 对每个阶段记录架构指标：跨层 include 数、双源枚举数、过渡 Adapter 数、Content 非规范目录资产数、缺少测试的模块数。

## 7. 推荐执行顺序

1. 阶段 0：先补 CI 和语义边界检查。
2. 阶段 1：身份模型双源，是减少后续补丁的最高收益项。
3. 阶段 3：登录、角色、会话、对局服务编排与 UE 冻结构筑同步推进。
4. 阶段 2：只提炼已证明通用的 MOBA 概念。
5. 阶段 4：最后处理资产与目录迁移。
6. 阶段 5：贯穿全程，但根治理文件删除必须单独提交和验证。

不推荐的做法：

- 不要一次性把 DBA_GameClient 重命名为新目录。
- 不要为了“层次纯洁”把所有 Arena 战斗代码上移到 GameMoba。
- 不要直接移动 .uasset/.umap。
- 不要同时迁移枚举、DataTable、网络协议、后端 DTO 和资产引用。
- 不要删除兼容类型后再用 Blueprint 或硬编码字符串临时补洞。

## 8. 本轮结论

当前工程的物理三层依赖已经具备基础约束，命名也大体可读；真正需要优先修复的是业务身份模型的所有权。在这一点收敛之前，继续扩展 GAS、登录、选角、HUD、VFX 或 DataTable 都会不断产生重复枚举、转换函数和补丁式适配。

因此，最佳下一步不是大规模整理目录，而是先执行“阶段 0 + 阶段 1”的最小可验证增量：建立语义边界守卫，设计中性构筑 DTO，在一条登录到 Dedicated Server 的完整链路上完成单一身份模型迁移，然后再逐步扩展。
