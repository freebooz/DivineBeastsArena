## 1. 总体架构概览

项目数据资产体系遵循 `DBA.DataAsset.NoHardcoding` 全局策略，理论上要求所有 Gameplay 数值、技能参数、冷却、消耗、UI 文案、运营配置均通过 DataAsset / DataTable / DeveloperSettings 驱动。实际实现呈现 **三种数据驱动入口并存** 的格局：

```
入口 1：UDBADataAssetBase 派生体系（GameCore 层基类）
  └─ UPrimaryDataAsset → UDBADataAssetBase → 7 个 typed 子类
      特征：DataId/DisplayName/Description/PrimaryTag/Icon/ThemeColor 公共字段

入口 2：直接继承 UDataAsset / UPrimaryDataAsset 的独立数据资产
  └─ UDBAAbilitySetDataAsset / UDBAZodiacHeroDataAsset /
     UDBABattleAttributeDefaultsDataAsset / UDBAPlayableSkillCatalogDataAsset /
     UDBAHeroBalanceConfig / UDBAStaticDataAsset / UDBAFixedSkillGroupDataAsset /
     UDBAZodiacAnimConfig_Generic + 12 生肖子类
  特征：每个类各自定义字段，未统一基类

入口 3：UDeveloperSettings 配置入口
  └─ UDBABattleAttributeDeveloperSettings / UDBAPlayableSkillDeveloperSettings
      特征：Config=Game，通过 TSoftObjectPtr 引用具体 DataAsset
```

**关键设计特征**：
1. **多套数据资产体系并存**：GameCore 层的 `UDBADataAssetBase` 与 DivineBeastsArena 层的独立 `UDataAsset` 子类未统一，存在重复设计。
2. **DataTable 软引用为主**：大多数数据资产通过 `TSoftObjectPtr<UDataTable>` 引用 DataTable，配合异步加载。
3. **异步加载边界清晰**：`LoadDataTable`（已加载则返回，否则发起异步请求并返回 nullptr）+ `RequestDataTableAsync`（非阻塞）模式贯穿多个数据资产类。
4. **DeveloperSettings 配置入口仅 2 个**：覆盖战斗属性和技能目录，其他系统未提供项目级配置入口。
5. **校验接口未普及**：仅 2 个类实现 `IDBAValidatableInterface`，其他数据资产缺少运行时校验。
6. **大量硬编码路径残留**：`DBAConstants.h` 定义 20+ 编译期路径常量，Widget/AnimConfig/LoginFlow 等多处直接写死 `TEXT("/Game/...")`。

### 2.1 UDBADataAssetBase（GameCore 层基类）

文件：`DBA_GameClient/Source/GameCore/Public/GameCore/Data/DBADataAssetBase.h`

继承：`UPrimaryDataAsset`

## 4. 异步加载与校验机制

### 4.1 异步加载边界

项目数据资产普遍采用以下加载模式（以 `UDBAZodiacHeroDataAsset` / `UDBAStaticDataAsset` / `UDBAAbilitySetDataAsset` 为代表）：

```cpp
// 已加载则返回，否则发起异步请求并返回 nullptr
UDataTable* LoadDataTable(const TSoftObjectPtr<UDataTable>& DataTablePtr) const;

// 非阻塞请求加载
void RequestDataTableAsync(const TSoftObjectPtr<UDataTable>& DataTablePtr) const;
```

**防重复请求**：通过 `mutable TSet<FSoftObjectPath> RequestedDataTableLoads` 记录已发起的异步请求，避免重复加载。

**评估**：
- 符合 `DBA.UI.EventAsync` 策略的非阻塞要求。
- 缺点：查询接口在首次调用时返回空结果，调用方需自行处理"数据未就绪"情况，缺少明确的事件通知机制（如 OnDataTableLoaded 广播）。

### 4.2 IDBAValidatableInterface 校验接口

仅以下 2 个类实现 `IDBAValidatableInterface`：
- `UDBABattleAttributeDefaultsDataAsset`
- `UDBAPlayableSkillCatalogDataAsset`

**未实现校验接口的类**：
- `UDBAAbilitySetDataAsset`（仅有 `ValidateDataIntegrity` 方法但非接口实现）
- `UDBAZodiacHeroDataAsset`（同上）
- `UDBAStaticDataAsset`（仅 `WITH_EDITOR` 下 `IsDataValid`）
- `UDBAFixedSkillGroupDataAsset`、`UDBAHeroBalanceConfig`、`UDBAAbilitySlotConfigAsset` 等

**评估**：校验机制覆盖严重不足，缺少统一的运行时数据校验入口。

### 4.3 编辑器数据验证

`UDBAStaticDataAsset` 在 `WITH_EDITOR` 下重写 `IsDataValid(FDataValidationContext&)`，通过 `ValidateLoadedTableRowCount` 检查表行数。其他数据资产未提供编辑器数据验证。

## 6. DataTable 异步加载评估

### 6.1 加载模式一致性

`UDBAZodiacHeroDataAsset`、`UDBAStaticDataAsset`、`UDBAAbilitySetDataAsset` 三个数据资产类均采用相同的异步加载模式：

```
查询接口（GetXxxTable）
  → LoadDataTable(软引用)
    → 若已加载：返回 UDataTable*
    → 若未加载：调用 RequestDataTableAsync(软引用)，返回 nullptr
  → 调用方收到 nullptr 时跳过本次查询，等待下次查询时表已加载完成
```

**优点**：
- 完全非阻塞，符合 GameThread 安全要求。
- `RequestedDataTableLoads` 集合防止重复请求。

**缺点**：
1. **缺少完成事件**：调用方无法得知"表已加载完成"事件，只能通过轮询或下次查询时偶然发现。
2. **无错误回调**：异步加载失败时无明确错误通知。
3. **无超时机制**：若资源加载卡住，调用方将永远收到 nullptr。
4. **模式重复**：三个数据资产类各自实现 `LoadDataTable` / `RequestDataTableAsync` / `RequestedDataTableLoads`，未抽取为公共基类或工具类。

**建议**：抽取 `FDBAAsyncDataTableLoader` 工具结构体，提供 `Load` / `RequestAsync` / `OnLoaded` 完成事件，统一复用。

### 6.2 UDBAFixedSkillGroupLibrary 兜底逻辑

`UDBAFixedSkillGroupLibrary::GetFixedSkillGroupById(...)` 采用三级策略：
1. **缓存命中**：返回缓存资产。
2. **异步加载**：发起异步请求，返回 nullptr。
3. **兜底 Transient**：创建临时 Transient 资产防止空指针。

**评估**：兜底 Transient 策略可能导致运行时使用未配置的默认值而掩盖配置错误，建议在兜底路径输出中文警告日志。
