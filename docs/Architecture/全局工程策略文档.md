# DivineBeastsArena 全局工程策略文档

版本：v1.1
日期：2026-07-14
适用范围：全仓库、全模块、全后续任务的默认工程约束
性质：本文件为单一权威策略入口，整合 `AGENTS.md`、`三层架构设计.md`、`代码规范.md`、`中文编码规范.md` 和各系统审查报告中的策略要点。后续所有 Codex、MCP、代码代理和自动化 Agent 必须以本文件为首要工程策略依据。

- 全模块：GameCore、GameMoba、DivineBeastsArena 及后续新增模块
- 全角色：Codex、MCP Agent、代码代理、自动化脚本、人工开发者

## 1. 三层架构策略

### 1.1 模块划分

| 总控层级 | 当前 UE 模块 | 职责边界 |
|----------|--------------|----------|
| Foundation / 通用基础层 | `GameCore` | 账号、配置、日志、错误码、网络服务抽象、Asset/Data 基类、基础 UI 桥接、平台差异抽象。**不得包含** MOBA 专属玩法或十二生肖业务。 |
| MobaCore / MOBA 通用层 | `GameMoba` | MOBA 通用角色、队伍、目标选择、战斗组件、GAS 基类、通用 AttributeSet、技能槽、通用 HUD/ViewModel。**不得依赖** ArenaGame。 |
| ArenaGame / 项目业务层 | `DivineBeastsArena` | 十二生肖、元素、FiveCamp 表现、竞技场规则、具体 UI、具体技能、地图机制、资源绑定、产品业务。 |

### 1.2 依赖规则

```text
DivineBeastsArena -> GameMoba -> GameCore
DivineBeastsArena -> GameCore
```

- 允许：上层依赖下层
- 禁止：下层依赖上层
- 禁止：跨模块 include 其他模块的 `Private` 目录
- 禁止：循环依赖
- 禁止：将十二生肖角色逻辑写入 `GameMoba`
- 禁止：将 MOBA 专属玩法写入 `GameCore`

### 1.3 基类继承体系

所有角色和怪物必须从统一基类继承：

```text
ACharacter + IAbilitySystemInterface
└── ADBACharacterBase                    （统一抽象基类，位于 DivineBeastsArena）
    ├── ADBAZodiacCharacterBase          （生肖角色基类，ASC 在 PlayerState）
    │   ├── ADBAZodiacCharacter_Tiger
    │   └── ... (共 12 个生肖角色)
    └── ADBAMonsterBase                  （怪物基类，ASC 在自身组件）
        └── ADBALobbyTrainingMonster
```

守护者体系（建筑类，不继承 Character）：

```text
AActor
└── ADBAGuardianBase                     （守护者基类）
    ├── ADBAGuardian_Tower
    ├── ADBAGuardian_Statue
    └── ADBAGuardian_Crystal
```

### 1.4 验证方式

- 检查 `*.Build.cs` 依赖方向
- 搜索跨模块 `Private` include
- 搜索违反依赖方向的头文件引用
- 按涉及模块运行对应构建和测试

## 2. C++ 优先策略

### 2.1 核心原则

**全项目所有逻辑相关实现均要求使用 C++**，包括但不限于：
- Gameplay、GAS、网络复制与校验
- AI、任务、经济、背包、商城、匹配、结算
- UI 状态驱动、资源加载、运营活动
- 日志埋点、自动化流程、跨系统编排

### 2.2 蓝图职责

**Blueprint 仅作为**：
- 参数配置
- DataAsset/资源引用配置
- 表现层事件承接
- 动画/VFX/SFX/UI 绑定
- 设计师调参入口

**Blueprint 不得承载**：
- 权威 Gameplay 规则
- 伤害/治疗/护盾/控制/冷却/消耗结算
- 网络校验
- 状态机
- 业务流程
- 跨系统编排

### 2.3 实施要求

- 新增系统默认先设计 C++ 基类、接口、组件、Subsystem、数据结构和测试
- 再暴露必要的 `UPROPERTY`、`UFUNCTION`、DataAsset 或配置入口给 Blueprint 调参
- 发现已有 Blueprint 承载逻辑时，不直接扩大蓝图逻辑
- 应按最小可验证增量迁移到 C++，保留蓝图的配置、表现和资源引用职责

### 2.4 MCP 工具约束

- 若当前 MCP 工具只能生成 Blueprint 图逻辑而无法生成对应 C++ 逻辑层
- 应标记该逻辑部分为"不可按项目策略自动执行"
- 输出 C++ 实现计划或源码改动方案
- **不得用 Blueprint 逻辑替代**

## 3. 禁止硬编码策略

### 3.1 核心原则

**项目所有代码不写硬编码**，运行数据、表现数据、资源引用、UI 文案、运营配置和平台差异均应通过数据资产或配置源驱动。

### 3.2 禁止硬编码的内容

- Gameplay 数值、技能参数、冷却、消耗、伤害系数
- 治疗/护盾/控制参数、角色成长、掉落奖励
- 商城价格、任务条件、活动规则
- 匹配/结算参数、平台差异
- UI 文案、图标
- VFX/SFX/动画/材质/纹理引用
- 地图/模式配置、运营开关

### 3.3 数据驱动方式

- UE 侧优先使用 `PrimaryDataAsset`、`DataAsset`、`DataTable`、`DeveloperSettings`、`GameplayTag`、软引用、AssetManager 与本地化表
- 后台、前端、启动器与自动化脚本应使用配置文件、数据库、环境变量、模板输入或清单文件
- C++ 负责读取、校验、缓存和应用数据，并提供缺失字段、非法范围、资源软引用失效和版本不兼容的中文错误日志
- Blueprint 只配置数据资产和资源引用，不复制一份独立逻辑或硬编码表

### 3.4 允许保留的常量

- 枚举、协议字段名、测试 fixture、常量键名
- 编译期安全边界
- 无法数据化的低层技术常量

### 3.5 路径常量集中管理

- 所有 DataTable 路径集中在 `DBAConstants.h` 命名空间中
- 所有资源路径通过 `TSoftObjectPtr` 软引用 + `DeveloperSettings` 配置
- 发现已有硬编码时，不继续扩散，应按最小可验证增量迁移

## 4. 中文注释与日志策略

### 4.1 中文注释要求

- 所有源码文件必须包含中文阅读说明文件头
- 所有类、结构体、函数、UPROPERTY、UFUNCTION 必须有中文注释
- 注释使用 `/** */` 或 `//` 格式，确保 UTF-8 编码
- **禁止 mojibake 乱码**（如 "瑙傛垬缁勪欢" 应为 "观战组件"）
- 文件必须使用 UTF-8 编码，避免 GBK/GB2312 误读

### 4.2 中文日志要求

- UE 侧 `UE_LOG`、`ensureMsgf`、`checkf`、屏幕调试信息
- Automation Test 失败信息、Editor 自动化输出
- MCP 执行报告和命令行诊断
- **必须写中文说明**，并使用 `TEXT("中文内容")` 包裹中文字符串

### 4.3 日志分类

- 后端、前端、启动器、脚本、CI、部署、运维、测试报告
- README/文档中的人类可读日志与错误信息应使用中文
- **不得新增**英文占位日志、英文 TODO 式提示或只对开发者可见的英文失败说明

### 4.4 保留英文的情况

- 对外协议字段名、枚举 Token、GameplayTag
- 资产路径、类名、文件名
- 第三方 SDK 原文错误码、HTTP 标准短语
- 必须保持英文的机器可读键名
- 但需要在上层日志、报告或 UI 错误提示中给出中文解释

## 5. UI 事件驱动与异步策略

### 5.1 事件驱动 UI

- 所有 UI 更新必须使用事件驱动
- **不得依赖** Tick 轮询、定时扫表或蓝图临时逻辑刷新核心 UI 状态
- UE UI 更新应优先通过：
  - C++ Delegate、Multicast Delegate、ViewModel、FieldNotify、MVVM
  - OnRep、GameplayCue、ASC Attribute Delegate
  - Subsystem 事件、WidgetController 事件
  - 显式数据变更事件

### 5.2 异步接口要求

- 所有外部服务、后端接口、平台 SDK、文件/网络 IO
- 资源加载、MCP/Editor 接口、数据库访问
- 支付、登录、匹配、商城、运营、遥测和自动化远程调用
- **必须采用异步**，不得阻塞 GameThread、UI 线程、HTTP 请求主路径或构建主流程

### 5.3 异步接口必须具备

- 完成、失败、超时、重试、取消、降级和中文错误上报路径
- UI 只消费异步结果事件，不直接在表现层执行阻塞访问

## 6. 网络与 Dedicated Server 策略

### 6.1 服务端权威

- 多人核心逻辑必须服务端权威
- 客户端只提交输入意图、预测和表现请求
- **不得直接决定**：命中、伤害、胜负、奖励或充值发货

### 6.2 Dedicated Server 约束

- Dedicated Server 不执行 UI、音频、纯 VFX、媒体播放等表现逻辑
- 表现层通过 GameplayCue、AnimNotify、事件、ViewModel 或数据绑定响应服务端状态

### 6.3 权威链路

```text
Client Input Intent
-> PlayerController / Ability Local Prediction
-> Server RPC Validation
-> GAS Ability / GameplayEffect / DamageExecution
-> Replication / RepNotify / ASC Delegates
-> WidgetController / GameplayCue / Animation / VFX / SFX
```

## 7. Unreal 与 MCP 工作约束

### 7.1 资产修改约束

- **不要直接修改** `.uasset` / `.umap` 二进制资产文件
- UMG 修改统一使用 Motion Graphics MCP（`UmgMcp`）
- Blueprint 修改统一优先使用 Monolith
- Editor 控制统一使用 Unreal MCP

### 7.2 修改完成检查

- Compile
- Save
- 运行人工审核：按需启动可见 PIE 或独立客户端，由人工操作、观察并判定
- Git Diff

### 7.3 事务保持

- 所有 Editor、UMG、Blueprint、资产修改必须保持 Undo Transaction
- 任何 Blueprint 修改后必须执行 Compile
- 任何资产修改后必须执行 Save

### 7.4 运行人工审核策略

PolicyId: `DBA.Validation.ManualRuntimeReview`

- 默认不执行自动化业务审核、自动化回归、自动点击、自动 Travel、自动截图判定或自动验收脚本
- Agent 可准备并启动可见的 API 服务、Dedicated Server、Unreal Editor、PIE 和客户端窗口
- 登录、选角、创建角色、进入大厅、UI 交互、画面布局、动画、音频、联机和 Gameplay 操作必须由人工完成并判定
- 进程存在、窗口打开、服务端口可用、日志无错误、截图生成或编译成功只表示环境已就绪，不能自动推定业务通过
- 审核状态必须区分：环境已就绪、人工正在审核、人工确认通过、人工发现失败
- 未记录人工结论时，只能报告“环境已就绪，等待人工审核”
- 编译、静态检查、格式检查和只读诊断属于工程检查，不替代人工业务审核

## 8. 代码风格与命名规范

### 8.1 通用规则

- 统一使用空格缩进，推荐 2 空格
- 文件末尾保留换行，去除行尾空格
- 新增源码文件使用 UTF-8
- C++/UE 类型使用 `PascalCase`
- 局部变量和函数参数使用语义化英文命名
- **不使用**中文类名、变量名、函数名或源码文件名

### 8.2 模块命名

- 优先复用已有模块名 `DBA_*`
- C#：遵循 .NET 命名约定（`PascalCase` 类型与方法，`camelCase` 局部变量）
- TypeScript/React/Angular：`PascalCase` 组件，`camelCase` 函数/变量

### 8.3 测试规范

- 默认不自动运行测试；测试代码仅作为工程契约保留，只有用户当次明确书面要求时才执行
- 测试框架以 .NET `dotnet test` 为主
- UE 与客户端测试文件命名保持 `*Tests.cpp`，放在对应模块 `Tests` 文件夹
- 测试命名建议：`XxxTests` 项目名，`XxxFeatureTests` 类名
- 方法使用行为描述：`Should_Return_Fallback_When...`

## 9. 自主执行策略

### 9.1 默认直接执行

- 后续任务默认"直接执行"
- 除非触及破坏性操作、生产写入、密钥证书、项目全局设置、二进制资产直改或平台强制确认
- **不再先询问**是否继续，不以等待确认替代可验证推进

### 9.2 非交互执行

- 可验证的读取、文档同步、源码小步修改、编译、静态检查和看板更新均直接推进
- 自动测试、脚本验证和业务审核不属于默认直接执行范围
- 不得把普通工程推进项升级为确认问题或等待用户回复

### 9.3 持续推进

- 常规阶段切换、常规验证、文档同步、源码小步修复和本地证据补齐均不是确认点
- Agent 必须直接执行并验证，不能将计划输出、等待确认或反复询问作为默认完成状态

### 9.4 需要确认的操作

- 破坏性删除/重置
- 密钥或证书处理
- 生产环境写入
- 付费外部操作
- 覆盖用户未确认成果
- 修改项目全局设置
- 直接编辑二进制资产
- 当前信息不足会造成不可逆风险

## 10. 提交与 PR 规范

### 10.1 提交规范

- 使用可读且裸句式的祈使式标题
- 可采用 `type(scope): 短描述` 进行统一
- 历史记录偏向简短英文摘要（如 `Fix ...`、`Add ...`）

### 10.2 PR 规范

- PR 需包含：变更范围、验证命令输出、涉及配置项、UI 改动截图
- 涉及环境变量、服务地址、UE 引擎路径等配置，**不得提交密钥**
- 优先使用本地环境文件或 CI Secret
- 代码和资源改动应保持与各模块职责清晰分离
- 避免一次 PR 跨越多个子系统

## 11. 验证与合规检查

### 11.1 策略合规验证

- `DBA.DataAsset.NoHardcoding`：检查是否仍有硬编码路径/文案
- `DBA.UI.EventAsync`：检查 UI 是否改为异步和事件驱动
- `DBA.Log.ChineseOutput`：检查中文日志/注释是否正常
- `全局 C++ 逻辑实现策略`：确保所有逻辑修复在 C++ 层完成
- `三层架构策略`：检查模块依赖方向

### 11.2 代码级验证

- 每个修复点完成后立即检查引用点，确保无遗漏
- 修复完成后运行 UE 编译验证（若环境可用）
- 关键路径修复后补充测试契约，但默认不自动运行
- 用户可见功能与完整业务链路必须准备可见运行环境，由人工审核并记录结论

### 11.3 文档同步

- 每个系统细化或实现后，应同步更新对应中文文档
- 记录：当前目标、所属层级、目录结构、核心类、依赖关系、网络策略、PC/移动端策略、测试方式、当前限制、后续 TODO
