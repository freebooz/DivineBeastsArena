# Divine Beasts Arena：总体架构设计与审查报告

版本：v1.0-reconciled  
来源：根据外部《神兽竞技场 / Divine Beasts Arena：UE5 MOBA 总体架构设计与审查报告 v1.0》附件整理，并按当前仓库总控提示词与 active goal 术语校准。  
用途：作为后续模块细化、C++ 类定义、GAS 落地、DataAsset 配置、网络同步、测试发布和上线运营的架构基线。

附件中使用的 `DivinePantheonType`、`PantheonSelect`、`PantheonStylePackage` 等术语，在当前项目中统一映射为 `FiveCamp` 表现包维度。当前 active goal 明确要求 `Zodiac / Element / FiveCamp` 三身份解耦，因此不得新增独立的 `Pantheon` 第四身份，也不得让 `FiveCamp` 参与技能组生成、伤害公式、元素克制或 TeamId 推导。

## 1. 项目总体理解

《神兽竞技场 / Divine Beasts Arena》是基于 Unreal Engine 5.8、C++、Gameplay Ability System 和 Dedicated Server 权威模型的多人在线十二生肖竞技场 MOBA 项目。项目核心不是自由装配技能池，而是固定的三身份组合：

| 维度 | 当前权威术语 | 职责 | 禁止事项 |
| --- | --- | --- | --- |
| 生肖身份 | `Zodiac` | 决定英雄身份、主题、外观剪影、生肖大招来源、中文显示名与短名。 | 不决定 `TeamId`，不直接决定元素克制。 |
| 自然元素 | `Element` | 决定元素技能、元素属性、元素克制、自然元素共鸣。 | 不决定 `TeamId`，不被 `FiveCamp` 改写。 |
| 五阵营表现包 | `FiveCamp` | 决定视觉主题、徽记、UI 图标风格、SFX/VFX 主题和表现资源选择。 | 不参与技能组、伤害公式、元素克制、TeamId。 |
| 对局队伍 | `TeamId` | 只表示比赛分队，例如 Red、Blue、Neutral、Spectator。 | 不映射为 Zodiac、Element 或 FiveCamp。 |

固定构建规则为 `Zodiac + Element -> FixedSkillBuild`。`FiveCamp` 只选择表现包，不改变技能合法性和数值。服务端在进入对局时必须重新验证最终冻结摘要，客户端 UI 或本地缓存不能伪造技能组。

## 2. 三层架构基线

当前仓库暂不做破坏性重命名，继续使用现有 UE 模块映射：

| 总控层级 | 当前 UE 模块 | 长期插件化目标 | 职责 |
| --- | --- | --- | --- |
| Foundation / 通用基础层 | `GameCore` | `DBAFoundationRuntime` 或 `ZodiacFoundationRuntime` | 账号、配置、日志、错误码、网络服务抽象、Asset/Data 基类、基础 UI 桥接、平台差异抽象。不得包含 MOBA 专属玩法或十二生肖业务。 |
| MobaCore / MOBA 通用层 | `GameMoba` | `DBAMobaRuntime` 或 `ZodiacMobaRuntime` | MOBA 通用角色、队伍、目标选择、战斗组件、GAS 基类、通用 AttributeSet、技能槽、通用 HUD/ViewModel。不得依赖 ArenaGame。 |
| ArenaGame / 项目业务层 | `DivineBeastsArena` | `DBAArenaGameRuntime` 或 `ZodiacArenaGameRuntime` | 十二生肖、元素、FiveCamp 表现、竞技场规则、具体 UI、具体技能、地图机制、资源绑定、产品业务。 |

依赖方向必须保持：

```text
DivineBeastsArena -> GameMoba -> GameCore
DivineBeastsArena -> GameCore
```

禁止：

- `GameCore` 依赖 `GameMoba` 或 `DivineBeastsArena`。
- `GameMoba` 依赖 `DivineBeastsArena`。
- 任意循环依赖。
- 任意模块 include 其他模块的 `Private` 目录。
- 为了“看起来模块化”创建大量空壳 UE Subsystem。
- 把十二生肖、元素克制或 FiveCamp 表现逻辑下沉到 Foundation。

## 3. Dedicated Server 与网络权威

竞技对局必须从第一天按 Dedicated Server 权威设计，而不是先做单机动作游戏再补网络。客户端可以提交输入、播放预测表现、展示 UI 和错误提示，但不得决定以下事项：

- 技能最终合法性。
- 命中、伤害、治疗、护盾和控制时长。
- `UltimateEnergy`、`ChainLevel`、`ElementResonanceLevel`。
- 胜负、结算、奖励、充值发货、订单状态。

推荐权威链路：

```text
Client Input Intent
-> PlayerController / Ability Local Prediction
-> Server RPC Validation
-> GAS Ability / GameplayEffect / DamageExecution
-> Replication / RepNotify / ASC Delegates
-> WidgetController / GameplayCue / Animation / VFX / SFX
```

Dedicated Server 不创建 Widget，不执行 UI、音频、纯 VFX、媒体播放和角色展示资源预览。表现层通过 GameplayCue、事件、ViewModel 或 RepNotify 消费服务端状态。

## 4. GAS 与战斗分层

GAS 需要拆分为通用 MOBA 能力与 DBA 项目能力：

| 层级 | 推荐职责 |
| --- | --- |
| `GameMoba` | `UMobaAbilitySystemComponentBase`、`UMobaGameplayAbilityBase`、`UMobaAttributeSetBase`、通用 DamageExecution、Targeting、Buff/Status 桥接、技能槽抽象。 |
| `DivineBeastsArena` | `UDBAAbilitySystemComponent`、`UDBAZodiacAbilityBase`、`UDBAElementAbilityBase`、`UDBAAbilitySetDataAsset`、`UDBAFixedSkillBuildDataAsset`、项目伤害公式和元素克制应用。 |

不得把所有战斗字段堆到 Character。长期建议：

- Character 承担 Avatar、Movement、Collision、Animation。
- PlayerState 持有跨死亡存活的 ASC 与对局身份状态。
- CombatComponent 承担战斗运行态。
- AttributeSet 承担 GAS 属性。
- GameState 承担公共对局状态。

`UltimateEnergy`、`ChainLevel`、`ElementResonanceLevel` 等权威状态只能有一个主存储位置，UI 通过镜像事件、RepNotify 或 ASC Delegate 读取，不得多处各自维护。

## 5. 角色构建与冻结摘要

角色创建、赛前选择和对局构建必须拆开：

```text
ZodiacSelect -> ElementSelect -> FiveCampSelect -> Confirm
Confirm -> FrozenBuildSummary
MatchStart -> Server Revalidation -> Ability Grant
```

冻结摘要建议包含：

- `PlayerId`
- `MatchId`
- `TeamId`
- `ZodiacType`
- `ElementType`
- `FiveCampType`
- `FixedSkillBuildRowId`
- `AttributePreviewHash`

Loading 阶段只能读取冻结摘要，不得根据 UI 草稿重新推导。服务端进入对局时必须按摘要和数据表重新验证技能组、属性预览和 TeamId。

## 6. UI、动画、VFX、SFX 边界

UI 和表现系统只消费逻辑事件，不直接驱动服务端权威逻辑。推荐链路：

```text
Ability / Combat Logic
-> GameplayEffect / GameplayTag / GameplayCue
-> Replication / ASC Delegate / RepNotify
-> WidgetController / AnimationComponent / VFXComponent / Audio Manager
-> Widget / Montage / Niagara / SFX / Camera Shake
```

禁止：

- Widget 直接持有具体 `AZodiacRatCharacter`、`AZodiacDragonCharacter` 等项目子类。
- Widget 直接硬耦合复杂战斗对象。
- UI 每帧全量轮询 ASC、Pawn、DataTable。
- Ability、DamageExecution 或 CombatComponent 直接创建 Widget。

推荐：

- 战斗 UI 订阅 WidgetController。
- Buff/Debuff/CC/Aura 来自 ASC Tags 或 Active GameplayEffect。
- `FiveCamp` 徽记、主题和 Cue 表现通过表现包 DataAsset 和软引用加载。
- Android 低配资源走平台变体和降级 Cue。

## 7. 资源与 Asset Manager

所有角色、技能、FiveCamp、皮肤、地图、UI 图标、VFX/SFX 和材质表现资源应优先使用软引用、Primary Asset 与 Bundle 管理。不得让 DataAsset 硬引用高配 VFX 导致 Dedicated Server 或 Android 包体膨胀。

建议优先建设：

- Foundation DataAsset 基类。
- PrimaryAssetType 命名规范。
- 平台变体与 Bundle 规则。
- 资源加载与释放策略。
- DataValidation 检查硬引用、缺失资源、错误层级引用。

Dedicated Server 包不得加载前台 UI、角色展示材质、高配 VFX、音乐、皮肤预览等客户端表现资源。

## 8. 运营与商业化边界

认证、Token、区服、公告、活动、商城、订单、支付回调、发货、邮件、奖励、封禁、异常消费和埋点均属于后端或 Foundation 服务抽象协作范围。UE 客户端只做请求、展示、缓存、错误提示和本地防抖。

禁止：

- 客户端内置可信价格。
- 客户端完成发货。
- 客户端发放奖励。
- UE 客户端承担订单签名、支付回调验证或幂等发货。

当前后端已有 API、Worker、ServerManagement、生产安全审计、备份恢复与 k6 证据基础。后续需要把 UE 客户端的服务抽象与后端 DTO、错误码、Token 刷新和断线恢复策略对齐。

## 9. 主要风险清单

| 风险 | 影响 | 当前处理原则 |
| --- | --- | --- |
| 三层架构只停留在文档 | 代码继续混在一个模块，后续迁移成本升高。 | 通过 `validate-unreal-module-boundaries.ps1` 和 Build.cs 检查依赖方向。 |
| GAS 项目层基类过重 | `UDBAAbilityBase` 变成新的万能类。 | 通用能力放 MobaCore，项目 Ability 只封装 DBA 上下文。 |
| 状态多处存储 | UI、CombatComponent、AttributeSet 状态不同步。 | 权威状态单点存储，UI 读复制镜像。 |
| UI 直连战斗对象 | 死亡、复活、重连、观战时 UI 失效。 | WidgetController/ViewModel 中介。 |
| 资源硬引用 | DS/Android 包体、内存和 cook 风险升高。 | 软引用、Primary Asset、Bundle 和平台变体。 |
| FiveCamp 被误用成阵营 | 破坏 TeamId 解耦与技能组规则。 | FiveCamp 只做表现包，不参与规则计算。 |
| 客户端商业化可信 | 支付、发货和奖励安全风险。 | 后端权威、客户端只展示和发起请求。 |

## 10. 后续开发路线图

短期仍以 MVP 和可验证闭环为优先：

1. 固化三层 Module / Build.cs 依赖规则。
2. 补齐 Foundation 的日志分类、错误码、基础 DataAsset、AssetManager 与服务抽象证据。
3. 补齐 MobaCore 的 PlayerState 持 ASC、HeroCharacter Avatar、CombatComponent、TargetingComponent、DamageExecution 基线。
4. 补齐 ArenaGame 的 `Zodiac + Element -> FixedSkillBuild` 数据资产与服务端验证。
5. 固化冻结摘要和赛前选择状态机。
6. 固化 `UltimateEnergy`、`ChainLevel`、`ElementResonance`、`ElementCounter` 的服务端规则表。
7. 固化 UI WidgetController 数据来源矩阵。
8. 固化资源 PrimaryAssetType、Bundle、低配替代和 DS 剥离策略。
9. 首个角色 Demo 跑通后再批量扩展 12 生肖 x 5 元素构建。
10. 核心战斗闭环稳定后，再扩运营、活动、邮件、充值和真实商业化。
